# 0004 Concurrent writes: versions, the page tree lock, news row locks and the order of redirect writes

## Context

Two editors can open the same page and save one after the other, and two requests can change the tree or the redirects at the same moment. MySQL InnoDB runs at its default REPEATABLE READ (the application does not change it): a transaction reads from a snapshot taken at its first plain read, and a locking read of a row that does not exist takes a gap lock, which blocks inserts by others into that gap. Two transactions that each hold a gap lock and then insert into the shared gap deadlock.

## Decision

Each mechanism protects one thing:

- **Optimistic version columns protect an edit from overwriting a newer one** (lost update between two editors). `page`, `page_translation`, `news` and `news_translation` have an integer `version` that the adapter sets (1 on insert, +1 on update; the value in the record is ignored). A form carries the version it was rendered from; a different stored version throws `StaleVersionException`, nothing is saved, and the form keeps the text with `admin.pages.stale` / `admin.news.stale`. An integer, not `updated_at`, because `DATETIME` has one-second precision. Moving a page (`movePage`, ↑/↓) keeps every version; dating a news item on its first publication leaves the item's version alone. The comparison runs after the lock below, so check and write are atomic.
- **The page tree lock serialises all page writes** and so protects the tree as a whole: no cycle from two crossing moves, sibling positions 0..n-1, path uniqueness across a subtree, the homepage rules. Every page write takes `SELECT id FROM page_tree_lock WHERE id = 1 FOR UPDATE` as its first step (`app/Model/Page/Database/DatabasePageTreeLock.php`); a missing lock row is an error, because the same query would then take only a gap lock and serialise nothing. Page writes refuse to run inside an already open transaction (`PageService::assertOwnTransaction()`): a joined transaction could have read rows from a snapshot older than the lock.
- **The news row lock serialises writes of one news item**; different items run in parallel (no global lock). Every news write starts with `lockNews()` (`SELECT … FROM news WHERE id = ? FOR UPDATE`) and also refuses an open transaction. A slug taken by a concurrent writer of another item is caught by the unique index `uq_news_translation_slug` and reported as a taken address (`InvalidSlugException::TAKEN`), never as a server error; the page adapter does the same for `uq_page_translation_path`.
- **No locking read of a news translation that may not exist.** `NewsService::writeTranslation()` reads the translation with a plain `SELECT`: `FOR UPDATE` on a missing row would gap-lock, and two first translations of different items in one gap would deadlock on insert. The plain read is current because every translation writer holds the item's row lock and the transaction's first plain read comes after it. Page writes do use `lockTranslation()` (`FOR UPDATE`); their gap locks are harmless because the tree lock already serialises them.
- **Redirects are written in the order record, then delete** (`moveRedirects()` in `app/Model/News/NewsService.php` and `app/Model/Page/PageService.php`). `record()` is an upsert of the old path; `deleteByPath()` removes a redirect from the new path and gap-locks when there is none. A news write calls `moveRedirects()` once per transaction, so no insert into `path_redirect` follows its DELETE's gap lock and concurrent news writers do not deadlock there. A page write may call it once per descendant (hierarchical strategy), so a later insert can follow an earlier gap lock; that is safe against other page writes only because of the tree lock.

## Consequences

- An editor who loses the race gets a message and keeps the text, instead of silently overwriting or being overwritten. Page writes are serialised site-wide, which is acceptable for a small site and would be the first thing to revisit under heavy editing.
- With the flat strategy a page write also calls `moveRedirects()` at most once, so it has the same record-then-delete shape as a news write. **Not covered by a test:** a page write and a news write running at the same time; a hierarchical strategy would need that case checked, because news writes do not take the tree lock.
- Tests: `tests/Model/Page/DatabasePageTreeLockTest.phpt` ("a second connection waits for the lock", missing row), `tests/Model/Page/PageServiceTest.phpt` ("every write takes the tree lock before reading the tree", stale versions, "every write refuses to run inside an already open transaction"), `tests/Model/News/Database/DatabaseNewsRepositoryTest.phpt` ("lockNews holds the row", slug-key clash), `tests/Model/News/NewsServiceTest.phpt` (two connections: "two items created at the same time do not block each other", "two items changing their slug at the same time do not block each other"), `tests/Presentation/Admin/PageEditTest.phpt` ("two browsers save the same translation version") and `tests/Presentation/Admin/NewsEditTest.phpt` ("a stale properties or translation save keeps the values with a message").
